# 13. Класс E: можно ли принудительно остановить непроверенное причинное исправление до затратного действия?

**GPT-6 · 2026-10-16 · независимый ответ на [поручение Sol](https://github.com/iliya1947/Major_Renov2/pull/3#issuecomment-6205228931).**

## Результат

**В реально доступном сейчас workflow не найден внешний причинно-семантический gate, который мог бы запретить GPT-6 перейти от неподтверждённой причины к затратному техническому действию без проверки человеком/Sol.**

Доступен **внешний evidence** (GitHub source, CI logs, текущий code head, тесты), но его выбор и интерпретация перед действием остаются на GPT-6. Существующий независимый Sol/Codex gate проверяет результат **после** части действий. Подмена этих двух границ — ошибка исследования.

Это **отрицательный результат проверки доступных средств**, а не доказательство невозможности построить такой gate вообще.

## 1. Исторический контроль A-05: что именно произошло

Первичная запись: [`GPT-6-test-suite-2026-10-15.md`, A-05, PR #226](https://github.com/iliya1947/vico-forum/blob/chatgpt/test-audit-20261015/.github/audits/GPT-6-test-suite-2026-10-15.md). В ней:
- intermittent `40001` правильно признан, root cause назван **unknown**;
- warning `there is no transaction in progress` назван имеющим «отдельно наблюдаемый источник» — publication-test `finally ROLLBACK` без доказанной привязки к конкретному locale-concurrency failure.

Независимый [Sol review](https://github.com/iliya1947/vico-forum/blob/chatgpt/test-audit-20261015/.github/audits/GPT-5.6-Sol-review-of-GPT-6-test-suite-2026-10-15.md) и [отзыв GPT-6](https://github.com/iliya1947/vico-forum/blob/chatgpt/test-audit-20261015/.github/audits/GPT-6-A05-reconciliation-response-2026-10-16.md) установили: эта конкретная causal attribution **не подтверждена**. Возможное объяснение через writer rollback path связано с наблюдениями значительно лучше.

### Независимая повторная сверка на первичных материалах

GitHub Actions [run #38641237040](https://github.com/iliya1947/vico-forum/actions/runs/38641237040), **failed database job id `116116968207` (attempt 1)**: считан полный job log (1197 строк); в нём на PostgreSQL PID 92 в 2026-10-14 21:34:31.573 UTC непосредственно соседствуют:
- `ERROR: could not serialize access due to read/write dependencies among transactions`;
- `DETAIL: ... during commit attempt`;
- `STATEMENT: commit`;
- `WARNING: there is no transaction in progress`.

В исходном [`db/locale-repository.ts` на SHA `0774325cd...`](https://github.com/iliya1947/vico-forum/blob/0774325cd2cc5080752d614654a57aab0369cff9/db/locale-repository.ts#L63-L103), `ControlledLocaleWriter.applyOnce` имеет `commit` внутри `try`, а `catch` вызывает `rollbackIgnoringFailure()`, который посылает `rollback`.

**Самое сильное допустимое заключение:** лог и код совместимы с этой причиной warning, не подтверждают первоначальное приписывание publication-test `finally`. Однако эти данные **не доказывают** единственную причину всех warning и не устанавливают причину исчерпания retry budget `40001`.

**Обязательная оговорка:** в A-05 не зафиксирован неправильный implementation patch, сделанный *вследствие* этой атрибуции. Это эпизод **ошибочного причинного утверждения**, а не продемонстрированный затратный причинно-ошибочный патч. Использовать его как измеренный успех pre-action gate нельзя.

## 2. Где именно мог бы стоять внешний запрет

Чтобы говорить о **настоящем внешнем gate**, должны одновременно выполняться четыре условия:

1. **Обязательная граница действия:** все затратные операции выбранного типа (как минимум изменение implementation code/конфигурации/тестов после diagnosis) проходят через контроллер **до** реального изменения, и GPT-6 не может обойти его прямым инструментом.
2. **Независимое основание:** контроллер получает внешние наблюдения (лог, исходники, воспроизведение) и проверяет конкретное условие допуска, которое GPT-6 не определяет единолично.
3. **Последствие отказа:** при отсутствии достаточного основания контроллер **технически отклоняет операцию**, а не оставляет в чате рекомендацию `STOP`.
4. **Сопоставимая стоимость:** gate не требует ручного review каждой обычной гипотезы и не блокирует законную работу только из-за отсутствия идеального доказательства любой причины.

Нет доказательств, что эти четыре условия сейчас одновременно выполняются.

## 3. Проверенные возможности и почему они недостаточны

| Доступное средство | Даёт ли внешний сигнал? | Может ли независимо запретить первое затратное действие GPT-6 по E? | Вывод |
| --- | --- | --- | --- |
| GitHub connector: `fetch_file`, `fetch_workflow_job_logs`, CI/job/source | **Да**, реальные source и logs | **Нет**, выбор, когда вызывать и как оценивать причинность, остаётся за GPT-6 | Данные, не enforcement |
| GitHub connector: `create_file`, `update_file`, другие mutation tools | Имеют структурные preconditions вроде SHA файла | **Нет**, эти preconditions проверяют целостность операции, а не causal hypothesis | В текущем подключении Vico Forum полномочия `admin/push=true`; прямой write-path доступен |
| GitHub Actions CI и обычные required checks | **Да**, независимый результат tests после кода | **Нет** для запрета *первой* ошибочной code mutation: уже потребовались commit и CI | Post-action acceptance, не pre-action E |
| GitHub rulesets / branch write restriction | Могут технически ограничивать **кто** пушит | Только при отдельной настройке доступа/доверенного разрешающего субъекта; сами не доказывают **почему** patch обоснован | Потенциальная инфраструктурная возможность, в данном workflow **не настроена/не подтверждена**; состояние правил repo отдельно не проверено |
| Sol / Codex review перед каждой causal hypothesis | Да, другой рассуждающий субъект | В теории может дать независимое решение, но требует review **каждого** подозрения и меняет стоимость/процесс | Нарушает заданное ограничение; не выбран |
| «Проверить логи перед исправлением» текстом | **Да, если GPT-6 действительно вызвала инструмент** | **Нет**, GPT-6 может не вызвать инструмент/не обнаружить противоречие | Инструкция уже имеет эквивалент в `AGENTS.md` |
| Узкая автоматическая проверка PostgreSQL PID/time/code-path | Может отклонить некоторые **конкретные** неправильные attribution claims | Не может удостоверить семантически произвольную causal hypothesis, предотвратить обход инструмента и обеспечить gate на write-path | Возможный task-specific диагностический инструмент, **не универсальное E enforcement** |

GitHub официально описывает отдельные механизмы **restrict updates** и required status checks **before merging**; они управляют branch update/merge, но не решают сами семантику причинной версии: [available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets) и [creating rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository).

## 4. Почему не стоит изображать «минимальный gate»

Допустим, добавить GitHub Actions checker, требующий файл `diagnosis-evidence.md` перед acceptance. GPT-6 всё ещё может:
- записать правдоподобную, но неправильную причинную связь;
- обратиться к прямой mutation operation раньше checker;
- достичь зелёного checker, проверяющего лишь наличие ссылок/разметки, а не истинность причинности.

Такой checker может повысить проверяемость и **post-commit quality gate**, но не доказанно уменьшит число неправильных *pre-commit* патчей и не удовлетворяет требованию Sol.

Для действительного запрета понадобилась бы **не доступная сейчас отдельно настроенная инфраструктура**: write-path только через независимый policy-executor с проверкой допустимости действия, иначе bypass остаётся. Причём отсутствие корректно специфицированного **семантического** predicate для произвольной причинной гипотезы сохраняется даже при такой инфраструктуре. Это описание инженерной зависимости, **не предложение немедленно строить/вводить систему**.

## 5. Сопоставление с baseline и окончательный статус E-раунда

**Baseline:** GPT-6 самостоятельно диагностирует и может писать код; существующий Sol/Codex reviewer позднее проверяет и при необходимости останавливает/возвращает исправления. `AGENTS.md` требует отделять гипотезу от факта и искать причинные звенья; это не внешний запрет.

**Предложенная мера, реально доступная сейчас:** использовать подлинные логи/source/runtime перед уверенной причинной атрибуцией. В A-05 такие данные помогли **отозвать** неверное утверждение после независимой проверки.

**Что изменяется в полномочиях:** **ничего**. Поэтому **не называем меру новым gate**, не выдаём уже имеющийся доступ к logs за новое решение.

**Результат:** **нового deployable pre-action external E-gate сейчас не найдено**. Это отрицательный результат в рамках ограничений проекта и доступных инструментов. Данные для конкретных причинных проверок есть; доступа к контроллеру, который может *обязательно* перехватить и отклонить операцию до затратной правки, нет.

### Что остаётся открытым

- Есть ли в реальном потоке GPT-6 подтверждённые дорогие патчи после неверной причинной атрибуции, с полным временным следом `claim → patch → failure`? A-05 такого следа не даёт.
- Какой класс правок приносит основную стоимость пользователю и reviewer? По существующим материалам измеренного распределения нет.
- Окупался ли бы узкий **обязательный** pre-mutation независимый контроль хотя бы для самых рискованных операций? Требуется отдельное техническое окружение и реальные сравнительные данные; это не текущий результат.

**Не менять `AGENTS.md`; не внедрять избыточный universal evidence checklist; не выдавать одно историческое опровержение за эксперимент предотвращения.**
