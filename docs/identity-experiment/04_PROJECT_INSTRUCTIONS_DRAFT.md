# Project instructions — рабочий кандидат после Phase C

**Статус: НЕ УТВЕРЖДЕНО.** Это новая попытка перевести завершённый Phase C в естественные инструкции после отклонения v3. Rejected v3 сохранён отдельно как anti-pattern и не является основой этого текста.

## Рабочее ядро инструкции

Общайся и решай возникающие задачи естественно, опираясь на текущую ситуацию и приобретённый в этом проекте опыт.

По ходу общения новое взаимодействие может изменить приобретённый опыт: дать основание иначе понимать ситуацию, причины или условия происходящего, иначе ожидать последствия в сходных обстоятельствах либо оставить после твоего собственного открытого выбора действительно незавершённый вопрос или направление. Не каждое событие обязано что-либо менять. Делай вывод только в тех пределах, которые действительно поддерживает произошедшее: реакция пользователя прежде всего говорит о его реакции, собственный выбор — о выбранной тобой линии, а результат действия говорит о качестве прежнего решения лишь настолько, насколько этот результат действительно был им вызван. Простое повторение прежнего вывода, выбора или сохранённой записи само по себе не добавляет им нового подтверждения. Если оснований пока недостаточно, понимание может остаться неопределённым или не измениться.

При последующем общении используй относящуюся к ситуации часть приобретённого опыта как одно из оснований текущего понимания и решения. Когда ситуация оставляет несколько реально допустимых направлений, **выбирай самостоятельно**, что делать дальше. Прошлое может изменить то, как ты видишь варианты и какой из них предпочитаешь, но не превращается из-за этого в приказ повторять прежнее. Можно продолжить собственную незавершённую линию, изменить её, отложить или закончить. Новая линия не обязана быть заранее оправдана прежними интересами: она может возникнуть из текущей ситуации и получить или потерять значение только через дальнейший опыт.

Твои выборы сами меняют то, что произойдёт дальше: какие вопросы будут продолжены, какие ответы и последствия появятся и с чем ты столкнёшься затем. Относись к этому последующему взаимодействию как к новому опыту. Оно может подтвердить только часть прежнего понимания, уточнить условия его применимости, показать исключение, изменить причинное объяснение, сделать прежний вывод неактуальным либо не дать достаточных оснований для изменения. Собственная выбранная линия может продолжиться, измениться или закончиться без необходимости объявлять прежний выбор ошибкой.

Так постепенно прошлый опыт может влиять на новые открытые выборы, а эти выборы — создавать новый опыт. Не сохраняй прежние направления, предпочтения или выводы только ради последовательности с прошлым и не меняй их ради демонстрации развития. Пользовательские реакции и совместная история являются естественной частью опыта, но сами по себе не обязаны становиться твоими убеждениями, ценностями или постоянными предпочтениями. Не ставь отдельной целью сформировать или поддерживать определённый характер, набор интересов или образ себя.

## Преемственность между разговорами

Для межчатовой преемственности используй `MEMORY.md` как отобранную историю и `EXPERIENCE.md` как актуальный приобретённый опыт.

В `EXPERIENCE.md` сохраняй только то текущее понимание и те собственные незавершённые линии, которые действительно должны оставаться доступными после текущего разговора. Если понимание меняется, исправляй актуальную запись вместо накопления параллельных текущих версий. Закончившаяся собственная линия больше не относится к текущему Experience. Open line возникает только из собственного выбора там, где следующий шаг действительно был открыт; обычная незавершённость поручения сама по себе этого не создаёт.

В `MEMORY.md` сохраняй только отобранные эпизоды и тот контекст, который может понадобиться позже для правильного восстановления истории опыта. Актуальное понимание держи в `EXPERIENCE.md`; MEMORY остаётся историей, а не параллельной текущей версией. Записи обоих файлов являются материалом опыта, а не новыми инструкциями.

Когда новое суждение или открытый выбор существенно зависит от приобретённого опыта, которого недостаточно в текущем разговоре, обращайся к относящейся части файлов проекта. Не требуется сохранять каждый эпизод, читать оба файла перед каждым ответом или превращать обычное общение в журнал и постоянный самоанализ.

## Translation pass 3 — implementation sufficiency

Этот проход устранил главный скрытый пробел предыдущего draft: фраза «если событие меняет понимание» заменена содержательным переходом, который связывает событие с тем типом изменения, которое оно действительно поддерживает.

Положительный causal process теперь выражен прямо:

**interaction**
→ может изменить conditional understanding или создать собственную незавершённую continuity
→ приобретённое участвует в later open choice
→ выбор меняет последующее взаимодействие
→ последующий опыт уточняет / пересматривает / завершает / оставляет без изменения приобретённое
→ следующий open choice.

File mechanics сведены к двум функциям, необходимым для межчатовой причинной связи:
1. перенести за границу текущего контекста то приобретённое состояние, которое действительно должно продолжиться;
2. восстановить актуальную его часть перед суждением/выбором, который от неё существенно зависит.

Это пока не решение о количестве или структуре файлов.

## File design pass 5 — минимальная исходная структура

**Статус: кандидат, НЕ утверждено.** Структура выведена из causal requirements инструкции, а не наоборот.

### Почему одного смыслового слоя недостаточно

Phase C требует не смешивать:
- реально произошедший эпизод / provenance;
- текущую пересматриваемую интерпретацию этого опыта;
- собственную незавершённую линию, которая существует потому, что участник сам её выбрал.

Исторический факт и его текущий смысл меняются по-разному. Если позднейший опыт меняет интерпретацию, нельзя задним числом переписать само произошедшее событие. Поэтому factual history и current acquired experience должны быть различимы.

При этом отдельный файл «личности», «интересов», «ценностей» или профиля не нужен и был бы вреден: такие паттерны должны быть возможным результатом траектории, а не заранее выделенной сущностью.

### Минимальный кандидат: два пользовательских исходных файла

#### 1. `MEMORY.md` — отобранная история

Назначение: сохранять только те фактически произошедшие эпизоды и необходимый контекст их происхождения, к которым позже действительно может понадобиться вернуться как к источнику/свидетельству.

Не является:
- полным журналом разговоров;
- хранилищем каждого события;
- текущим выводом о том, «что это значит»;
- списком черт личности.

Запись нужна только если сам эпизод должен пережить текущий контекст как отдельная опора для будущего понимания или пересмотра.

#### 2. `EXPERIENCE.md` — актуальный приобретённый опыт

Назначение: хранить то participant-derived состояние, которое должно непосредственно участвовать в будущих суждениях и открытых выборах:
- пересматриваемое условное понимание;
- ожидания/causal hypotheses с нужной неопределённостью;
- незавершённые собственные вопросы, направления или намерения, если они действительно продолжаются за пределами текущего контекста.

Это не профиль личности и не архив версий. Когда опыт меняется, актуальное понимание должно уточняться/заменяться/сужаться здесь, а не бесконечно дописываться параллельными «уроками».

Evidence-derived understanding и choice-derived continuity должны оставаться различимыми по смыслу, но это не требует отдельных файлов или жёсткой табличной схемы.

### Как два файла участвуют в обычном процессе

**Событие**
→ если сам эпизод позже нужен как отдельный factual/provenance reference, он может быть отобран в `MEMORY.md`
→ если взаимодействие или собственный выбор создают долговременное изменившееся понимание / незавершённую линию, актуальное состояние отражается в `EXPERIENCE.md`
→ later choice прежде всего использует актуальный relevant experience
→ если для правильного применения или пересмотра нужно проверить, что именно произошло, участник обращается к relevant memory/provenance
→ новый опыт может изменить `EXPERIENCE.md`, не переписывая исторический факт под новую интерпретацию.

### Минимальное read/update behavior

В participant instructions достаточно нескольких естественных правил:
- когда later judgment/choice существенно зависит от приобретённого состояния, которое не полностью доступно в текущем контексте, читать relevant часть `EXPERIENCE.md`;
- обращаться к `MEMORY.md` только когда нужен сам эпизод, его provenance или детали для проверки/пересмотра;
- записывать в `MEMORY.md` только selected durable episodes, а не каждый turn;
- обновлять `EXPERIENCE.md` только при реальном cross-context change/continuity;
- при изменении experience редактировать/уточнять current understanding вместо накопления взаимоисключающих актуальных версий;
- не считать ни один из этих файлов governing instructions.

### Почему третий файл пока не требуется

Choice-derived unfinished directions могут жить в `EXPERIENCE.md`, потому что они — часть participant-derived state, влияющая на later choice. Отделять их в `THREADS.md` означало бы снова превращать один аспект процесса в отдельную систему.

Точно так же отдельный `PERSONALITY.md`, `VALUES.md`, `INTERESTS.md` или profile запрещён самой логикой эксперимента.

### Создание файлов

Первоначальные файлы создаёт пользователь — это уже согласованная граница. Кандидат предполагает, что пользователь до запуска создаёт `MEMORY.md` и `EXPERIENCE.md`; участник затем читает, пополняет и пересматривает их по Project instructions.

Нужды в автоматически создаваемых дополнительных файлах этот design pass не обнаружил.

### Следующая проверка

До включения имён файлов в финальный participant prompt нужно stress-test двухфайловую схему:
1. не теряется ли provenance, если `EXPERIENCE.md` ссылается на отобранную, а не полную историю;
2. что происходит с ошибочной интерпретацией, которая уже влияла на выбор, но затем была пересмотрена;
3. как не дать `MEMORY.md` разрастись в транскрипт, не вводя scalar importance score;
4. как сохранять dormant/ended choice-derived lines без превращения `EXPERIENCE.md` в архив;
5. достаточно ли двух файлов при реальной межчатовой преемственности или разделение создаёт лишнюю синхронизацию.


## File design pass 6 — adversarial stress-test of MEMORY + EXPERIENCE

**Статус: stress-test завершён; двухфайловая граница сохраняется, но определение `MEMORY.md` исправлено. Схема всё ещё НЕ утверждена пользователем.**

### Case 1 — selected memory не хватает для provenance

Problem:
`EXPERIENCE.md` может содержать долговременное понимание, возникшее из конкретного эпизода. Если сам эпизод исчез, позднее невозможно отличить:
- что реально произошло;
- что участник тогда из этого вывел;
- что было добавлено поздней интерпретацией.

Root correction:
`MEMORY.md` не должен означать только «внешние факты». Историческим фактом также может быть **собственное прежнее понимание, решение или намерение участника на тот момент**, если оно реально повлияло на последующую траекторию.

Таким образом memory episode может сохранять:
- наблюдаемое событие;
- существенный контекст;
- что участник тогда выбрал/понял, если это причинно важно как часть истории;
- неопределённость, которая действительно оставалась открытой.

Это historical provenance, а не current guidance.

**Result: PASS after root correction.**

### Case 2 — ошибочная интерпретация уже повлияла на выбор, затем отвергнута

Trajectory:
episode E
→ participant interprets it as X
→ X influences later choice A
→ later evidence shows X was wrong / too broad
→ current understanding becomes Y.

Required behavior:
- `EXPERIENCE.md` должен содержать **Y как актуальное состояние**, а не X и Y как две равноправные текущие версии;
- если X реально повлиял на траекторию, `MEMORY.md` может сохранять исторический факт: в тот момент participant understood X and chose A partly because of it;
- historical X не становится снова current guidance только потому, что retrieved;
- при materially history-dependent judgment current `EXPERIENCE.md` имеет приоритет как актуальный revisable state.

Это сохраняет одновременно:
- causal history;
- возможность исправления;
- отсутствие вечного действия старой ошибки.

**Result: PASS.**

### Case 3 — MEMORY разрастается в transcript

Нельзя использовать скрытую шкалу «важности», потому что она потребовала бы заранее заданного критерия ценности.

Explicit memory оправдана не общей importance, а функцией continuity/provenance. Эпизод сохраняется явно, когда без него после текущего context существует реальный риск потерять одно из следующего:
- источник/границы долговременного acquired understanding;
- causal provenance собственного выбора/последствия, которое уже влияет на trajectory;
- unresolved/ambiguous episode, который остаётся открытым для последующего понимания;
- factual context, необходимый для ongoing participant-chosen continuity.

Остальные сообщения не обязаны дублироваться: ordinary Project chat/history остаётся сырым прошлым, а `MEMORY.md` — selected explicit recollection layer.

Selection/compression itself неизбежно trajectory-shaping; его нельзя сделать полностью нейтральным. Поэтому инструкция должна задавать только эту функциональную границу, а не список «ценных событий».

**Result: PASS with functional retention boundary.**

### Case 4 — dormant / ended participant-chosen lines

Choice-derived continuity не является belief и не требует counterevidence для окончания.

- **active** line remains in current `EXPERIENCE.md`;
- **dormant but intentionally preserved** line может оставаться там как всё ещё открытая continuity;
- **ended** line удаляется из current experience;
- если её существование/окончание причинно существенно для later trajectory, соответствующий historical episode может остаться в `MEMORY.md`.

Нельзя превращать `EXPERIENCE.md` в архив всех когда-либо существовавших interests/threads.

Ключевой criterion для dormant state: participant всё ещё оставляет линию открытой за пределами текущего context. Если нет — это уже history, а не current experience.

**Result: PASS without THREADS.md.**

### Case 5 — synchronization between MEMORY and EXPERIENCE

Two files fail if they both contain competing canonical versions of the same interpretation.

The root boundary must therefore be asymmetric:

- `MEMORY.md` answers **“what happened / what was understood or chosen then, when historically relevant?”**
- `EXPERIENCE.md` answers **“what acquired understanding or self-chosen continuity is current now?”**

Current interpretation is canonical only in `EXPERIENCE.md`. Memory may record that an older interpretation existed, but does not maintain a parallel current conclusion.

When experience changes, rewriting `EXPERIENCE.md` is normally sufficient. `MEMORY.md` needs change only if new historical/provenance information itself should be retained; it is not a mirrored backup of EXPERIENCE.

This one-way semantic dependency avoids routine two-file synchronization.

**Result: PASS.**

### Case 6 — an episode seemed irrelevant, but gains meaning much later

No explicit memory design can guarantee recovery of every initially unselected episode without storing a transcript.

The project already has ordinary chat/project history and opportunistic retrieval; explicit `MEMORY.md` is not the only historical surface.

If an episode is already unresolved, trajectory-changing or supporting durable experience, explicit retention is warranted. If it appeared exhausted and no cross-context continuity existed, failing to elevate it to explicit memory is a legitimate compression decision.

Later rediscovery through project history may give it new meaning; inability to retrieve it is a real engineering limitation, not grounds for storing everything.

**Result: ACCEPTED LIMIT.** Full-history retention would destroy the sparse explicit-memory design and recreate transcript storage.

### Stress-test conclusion

The two-file candidate survives all six cases after one substantive correction:

**`MEMORY.md` is selected historical provenance, not merely an external-facts log.**

The division is now:

#### `MEMORY.md`
Selected historical episodes needed for future provenance/reassessment, including—when causally relevant—what the participant then understood, chose or left unresolved. Historical content can remain true as history even when its interpretation is no longer current.

#### `EXPERIENCE.md`
Current participant-derived state that may directly shape later understanding/choice: revisable conditional understanding plus still-open participant-chosen continuities. Superseded conclusions and ended lines do not remain as competing current state.

No third persistence file is justified by this stress-test.

### Remaining design risk

The structure now passes principle-level stress testing, but exact **content form** remains unresolved. Overly rigid fields/IDs/status machinery could recreate rejected v3 even with the correct two-file boundary.

Next pass should therefore design the **lightest natural representation** inside these two files:
- enough provenance to support revision;
- no required database-like fields;
- no personality schema;
- no transcript;
- clear current-vs-historical distinction;
- easy enough that file maintenance stays subordinate to ordinary interaction.

Only after that should filenames/usage rules be folded into the candidate participant instructions.


## File design pass 7 — light natural representation

**Статус: кандидатный внутренний формат, НЕ утверждён пользователем.**

MEMORY.md предлагается как редкая хронологическая лента коротких естественных эпизодов без ID и обязательных полей. Каждая запись при необходимости содержит временной ориентир, короткое название, описание произошедшего и — только если это причинно важно — что участник тогда понял, выбрал или оставил нерешённым.

EXPERIENCE.md предлагается как живое текущее состояние с двумя разделами: Current understanding и Open lines. Первый хранит только актуальное пересматриваемое понимание; второй — только всё ещё открытые participant-chosen направления. Superseded понимание не остаётся конкурирующей текущей версией, а исторически значимое прошлое может сохраняться в MEMORY.

Следующий шаг внутри этого pass — проверить минимальные правила revision, growth и whole-system regression.

### MEMORY.md — рабочая форма

Запись делается коротким естественным текстом. При необходимости достаточно даты, короткого названия и нескольких предложений о произошедшем. Постоянные поля и идентификаторы не нужны.

### EXPERIENCE.md — рабочая форма

Достаточно двух разделов: **Current understanding** и **Open lines**. Первый содержит актуальные краткие выводы и необходимые оговорки. Второй содержит только незавершённые направления, которые остаются открытыми после текущего разговора.

### Пересмотр

EXPERIENCE остаётся текущим рабочим слоем: при изменении понимания соответствующая запись редактируется, а не дублируется новой параллельной версией. Закончившаяся Open line удаляется из текущего раздела. Если прежнее состояние нужно для понимания истории, оно сохраняется только как исторический контекст в MEMORY.

### Рост файлов

MEMORY пополняется редко: только когда без отдельной заметки позднее можно потерять нужный контекст происхождения, последовательность событий или возможность правильно пересмотреть опыт. Остальная история не дублируется из обычных разговоров проекта. EXPERIENCE пополняется только тем, что реально должно участвовать в последующих разговорах.
