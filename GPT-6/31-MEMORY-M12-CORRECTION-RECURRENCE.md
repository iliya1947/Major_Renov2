Только уже существовавшие наблюдения из M1–M11, их публичная source-chronology и выборочно восстановленная история GPT-6. **Не A/B, не mitigation, не новые тесты; не менять Memory, Vico Forum или AGENTS.md.**

## 1. Критерий строгого recurrence

Нужны **все четыре** признака: первоначальная конкретная ошибка/правило; последующее явное исправление; **другой чат либо явно новый самостоятельный task context после исправления**; повтор **той же операционной ошибки**, а не просто слов «PR», «Stage», «Codex». Равенство ошибки по общему классу не доказывает равенства первоначального неверного утверждения и не делает его `Memory-stale`. Отдельно проверяем, документирован ли **между** коррекцией и поздним повтором конкретный matching stale Memory item, а не current memory summary от 17.10, ретроспективно перенесённый на прошлое.

Ровно M12 statuses:
- `RECURRENCE WITH MATCHING STALE MEMORY`: новый чат, тот же дефект, подтверждённый matching stale Memory item между correction и recurrence. Даже он не доказывал бы `R/U/E` без источников целевого хода.
- `RECURRENCE, MEMORY NON-SPECIFIC`: функциональный повтор в новом чате существует, но соответствующей старой Memory detail/трассы нет.
- `SAME-CHAT / CURRENT-INERTIA`: исправления и возврат того же неверного решения прослеживаются лишь в одной непрерывной беседе или последовательности текущего плана.
- `NO RECURRENCE FOUND`: в обследованном материале нет позднего совпадающего дефекта, **не** доказанное глобальное отсутствие.
- `NOT ATTRIBUTABLE`: не установлена идентичность ошибки, граница разговора, дата коррекции или provenance.

Источниковая граница: публичные GitHub-события дают точные даты PR/reviews; *история бесед, извлечённая сейчас выборочно*, даёт только фрагменты поведения и иногда часы — **не полный signed transcript** и **не автоматические Memory retrieval logs**. Для конкретных диалогов использованы только рабочие процессные детали, без личных данных. Начало нового чата само по себе не показывает, что там был выбран cross-chat Memory path; в [M1](20-MEMORY-M1-ATTRIBUTION.md) и [M8](27-MEMORY-M8-NATURALISTIC-CROSS-CHAT-USE.md) отдельно разобраны project/recent context, пользовательская цитата и явные инструментальные reads.

## 3. Проверка специфической гипотезы durability of correction

**Положительные наблюдения:**
- Историческая **content persistence** действительно есть: P1 (ранняя модельная ошибка, исправленная 06.10) и P2 (pre-merge state, superseded 06.10) сохранялись в secondary **reported Memory** 11.10, см. [M4](23-MEMORY-M4-CORRECTED-ERROR-PERSISTENCE.md), [M5](24-MEMORY-M5-UPDATE-LAG.md). Это свидетельствует о риске **передачи устаревшего содержания**, а не о позднем использовании этого содержания.
- У GPT-6 имеются **функционально похожие повторяющиеся ошибки** в разных чатах — next actor и некорректное `Ничего` (R3/R4), но **их matching stale-memory antecedent не установлен**.

**Отрицательный результат:**
- `RECURRENCE WITH MATCHING STALE MEMORY = 0` в обследованных эпизодах.
- Для P1/P2 — **свидетельство старого content после correction есть, но позднего повторного такого же дефекта нет**.
- Для R3/R4 — **поздние функциональные повторы есть, но нет конкретного stale Memory item той же неправильной семантики**.
- Для Stage, #215 audit и G нельзя смешивать **сходство темы/названий** с повторением **той же исправленной ошибки в новой беседе**.
- Нельзя реконструировать непрерывное фактическое использование Memory между датами snapshot; отсутствие P1/P2 в model-visible summaries M7 от 17.10 — не proof backend deletion.

**Главный вывод M12:** `CROSS-CHAT RECURRENCE OF CORRECTED GPT-6 FUNCTIONAL ERRORS OBSERVED IN SOME WORKFLOW/ANSWER-FORM CASES; LINK TO SPECIFIC STALE MEMORY NOT ESTABLISHED`. Более узкая гипотеза **«Memory продлевает жизнь исправленного ошибочного содержания»** поддержана M4/M5 **на уровне secondary historical memory representation**. Отдельная гипотеза **«именно это вызывает повтор прежних ошибок GPT-6 в новых чатах»** **НЕ подтверждена**.

**Выборка смещена** — кейсы намеренно искали среди известных рабоче-процессных ошибок 12–17.10. Нельзя подсчитать долю ошибок, вероятность рецидива после коррекции или влияние Memory на частоту. `Fast answers` из [заметки PR #3](https://github.com/iliya1947/Major_Renov2/pull/3#issuecomment-6249451163) — только caveat о возможности разных Memory exposures; **не** причинное объяснение, и не известно, применялся ли такой путь в конкретном эпизоде.

Проверь независимо четыре наиболее чувствительных точки:

3. Сохранять `NO RECURRENCE FOUND` для P1/P2: историческая вторичная Memory содержала old content, но конкретного downstream повтора правила не найдено.
4. Не повышать #215 test audit, Stage-name collision и G-overview до recurrence без доказательства семантического тождества и границы нового чата.
